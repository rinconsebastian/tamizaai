# Design

## Context

See proposal.md for the motivation and the specs for the behavior. This change comes after `add-small-sample-warnings` in the program (P1-6 before P1-7), which was implemented and archived on 2026-11-05, ships in the same release (D11), and depends on it for what it does not define:
- the base n of a widget (the sum of the declared base column, else of a ratio's denominator; over several answers of a declared answer column, the largest per-answer sum; a widget n only when its indicator declares a base column or an answer column; that change's D2 to D4);
- the answer columns of indicator column metadata (`categories`: `single` or `multiple`), which `add-indicator-column-metadata` stores in `script_versions.columns`, and which `QueryAsync` reads into `IndicatorBases` for `Plan` (that change's D5);
- the base n line under a widget (`display.showN`, the dashboard's `showN`) and the figures `numerator`, `denominator` and `n` of each row.

It also follows `add-chart-annotations` D4, which adds a flag that widgets never save, `IndicatorQueryRequest.Overall`, set from the widget's display by the code that sends the request (the page, the email, the widget workbook and `get_widget_data`), so that `WidgetConfigInput`, `WidgetConfig`, `queryFor` and the stored config never hold it, and a statement for a reference line's overall value. **Decided with the user on 2026-11-04:** the derived query flags of the program travel as request flags, so this change's `unfiltered` flag follows that pattern (D3); this design first planned it as a field of `WidgetConfigInput`. The change was written against the main specs and the code as they were after `add-indicator-column-metadata` and `add-widget-context` were implemented and archived (2026-11-04), and rebased on 2026-11-05 on the main specs and code after `add-chart-annotations`, `add-declared-category-order` and `add-small-sample-warnings` were archived (see "Spec ownership" and the last bullet below), so what they added is stated in the past tense, and the pieces it works on are named by function or constant, not by line, since the lines move. The pieces this change works on:

- **The tile.** `StatWidget` (`indicators/stat-widget.ts`) draws `<p class="break-all text-4xl font-semibold">` (36 px, and `break-all` may split a number) over `plotted()` in `text-sm`, a line that only screen readers keep (`sr-only`) when the widget hides its caption (`captionShown`, `add-widget-context`). It reads `rows[0].value` and registers export parts with `stat: { value, description }` (`ExportParts.stat` in `export-parts.ts`, its description null for a widget that hides its caption). Its root centers its column with `justify-center`, or with `justify-center-safe` when the tile has a subtitle or a footnote (`hasTexts`), so the figure stays whole and the label is the part cut. The same component draws the two total tiles of an indicator test in the script editor (`script-editor/indicator-view.ts`, boxes `h-28`). Every host gives it a definite height: the grid tile body (`widget-grid.ts`, `min-h-0 flex-1 overflow-hidden p-3`) under a header that is taller with a subtitle, the widget view's plot box, which a footnote shortens, the form's preview (`widget-dialog.ts`, `h-40` for a stat tile) and the script editor's `h-28`. The default tile is 3 by 2 cells (`defaultSize` in `grid-layout.ts`) of 72 px rows (`rowHeight`); `add-widget-context` D5 measured its body at 81 px on a 1,280 px page. The only container query in the indicators today is the pie's `@container` (`pie-widget.ts`). The Spanish interface calls the kind "Cifra destacada" (`es.json`).
- **The figure elsewhere.** The widget image writes the value at a fixed 36 px and weight 600 in one text element, never wrapped (`composeImage` in `widget-export/image-layout.ts`, after the title, the subtitle, the notes above and the caption line, which a stat tile leaves null); its `wrap()` cuts a word wider than a line at a letter. The description follows at 14 px, when the widget shows its caption, and then come the notes below, the footnote and the footer. The email body writes the value at 24 px (`ReportHtml.Stats`), in a cell with the title, the subtitle, the value, the caption (left out when hidden), the notes and the footnote; the plain text writes `- {title}: {value}` with the caption in parentheses (left out when hidden), then the subtitle, the notes and the footnote on lines of their own. The email workbook's "Summary" has one line per tile (`ReportWorkbook`), then each widget's subtitle, footnote and notes; a widget workbook writes a tile as one column and one row (`WidgetWorkbook.TableOf`), and its "Summary" lists the project, the dashboard, the version and the source, the widget, its subtitle, its indicator, what it plots, the filters, the publication and the export, the rows, the footnote and the notes. Printing uses the page's DOM.
- **The stat query.** `WidgetQuery.For` (`Indicators/WidgetQuery.cs`, a positional constructor call) and the UI's `queryFor` (`widget-view.ts`) drop `groupBy` for a stat tile. `IndicatorQueryBuilder.Plan` builds `aggregate` (the sum, or `sum(num) / nullif(sum(den), 0)`) and `plotted` (one row's value) with the `rowFilter`; with no group the statement is `SELECT NULL::text, (aggregate), NULL::text … HAVING (aggregate) IS NOT NULL`. Every consumer reads a tile as `rows[0].value`: the page, `ReportDataBuilder.ReadWidgetAsync` and MCP's `Row()`. `BoxQueryBuilder` is where the box plot computes its quartiles and mean (below).
- **Percentiles already exist.** `BoxQueryBuilder` computes `percentile_cont(ARRAY[0.25, 0.5, 0.75]) WITHIN GROUP (ORDER BY x)` (linear interpolation, pandas' default) and the mean as `sum(x) / count(*)`, over finite values only (box plot design D3).
- **The query.** `IndicatorQueryRequest(Config, ChartType, DashboardFilters)`. `IndicatorDashboard.QueryAsync(projectId, input, chartType, ct, dashboardFilters)` validates (`CheckConfig` with the chart type, or null when the request has none), takes a slot, opens one read-only transaction with a 25 s statement limit, plans and reads. Plan errors become a 400 (`IndicatorEndpoints.QueryAsync`), which the page shows as an error alert and an email as "no longer fits". Callers of `QueryAsync`: the endpoint (which MCP's `query_indicator` calls too, with a chart type and no dashboard filters), `ReportDataBuilder.ReadWidgetAsync` (the email and, through `BuildWidgetExportAsync`, the widget workbook, both through `WidgetQuery.For`) and `McpDashboardTools.WidgetDataAsync` (`get_widget_data`). `add-chart-annotations` D4 added an optional `overall` argument to `QueryAsync` (last, after `dashboardFilters`), set by the last two from `WidgetQuery.Overall` and by the endpoint from `request.Overall`; `unfiltered` joins it after it (D3). The dashboard filters' WHERE comes from `PlanDashboardFilters` and is joined to the widget's own in `Plan`.
- **The stored config.** `WidgetConfigInput`, `Normalize()` and `WidgetConfig` (`Indicators/IndicatorModels.cs`); `WidgetDisplay`, whose members end `Color`, `Ramp`, `Orientation`, `Labels`, `Subtitle`, `Footnote`, `Caption`, `Unit`, `ShowDescription` (`add-indicator-column-metadata` and `add-widget-context` appended the last six), then `ReferenceLines`, `Interpolation`, `DataLabels` (`add-chart-annotations`), `Order` (`add-declared-category-order`), `MinN` and `ShowN` (`add-small-sample-warnings`), each `WhenWritingNull` with a `Description` the MCP schema shows, and `Normalize()` returning null when every member is unset. `CheckConfig` and `CheckDisplay` (`IndicatorValidation.cs`; the per-kind rules are skipped when the chart type is null, and `CheckLabels` and `CheckContext` follow them). A PATCH re-checks the config only when it sends one or a chart type (`DashboardEndpoints`). The UI's `savedConfig` (which spreads `queryFor`) and `displayFor` (`widget-view.ts`) decide what a kind saves, and `displayFor` already keeps the labels and the five texts on every kind; the form rebuilds the config in `formConfig` and `displayDraft` (`widget-dialog.ts`) and maps error keys in `fieldFor`. The view's query key is `{type, queryFor(config), dashboardFilters}` (`key` in `widget-view.ts`), to which `add-chart-annotations` added `overall: true` for a widget that asks for it.
- **Ratios and the series statement.** `aggregate` is the one place a ratio is summed: the plain path, the ungrouped stat path, the `ORDER BY` of a sort by value, the pie's domain (`PieDomain`), and the series statement (`SeriesQueryBuilder`), whose `src` CTE reads `{from}.*` with the series text and kind (folded series become one "Other" value) and whose `grp`, `cell`, series-total and grand-total branches each take `aggregate`. `GroupTotal`, `SeriesTotal` and `GrandTotal` values are already nullable; a cell's `IndicatorRow.Value` is not.
- **Docs.** `docs/indicators-dashboard.md`: the "Stat tile" row of the widget types table says a stat tile "Says over how many rows it was summed" and that its group column is "Optional"; neither is true. "Preparing indicators for dashboard filters" warns that a `select_multiple` column added up across values counts a submission once per option. "Words around a widget" says that a 3 by 2 stat tile with a subtitle and a footnote keeps its figure whole and cuts its label, and "Images" and "Workbook" describe what a tile's image and workbook hold. Two sentences that `add-small-sample-warnings` wrote become false with this change: `docs/scripts.md` "A declaration changes no plotted value." and, in `docs/indicators-dashboard.md` "The lines under a widget", that a 3 by 2 stat tile with a subtitle, a footnote and an n line "keeps about 25 pixels for its figure and is cut by the tile, so give a stat tile that shows its lines 3 rows".
- **After the rebase on `add-small-sample-warnings` (2026-11-05).** What that change left that this one builds on: `IndicatorBases(BaseColumn, Answers, Missing)` in `BaseQueryBuilder.cs`, whose `Answers` holds the declared answer columns by name only, since the kind does not change the n (task 3.4 adds the kind); `BaseQueryBuilder.Counted` and `CountsAnswers`, the n across answers, called from `IndicatorQueryBuilder.Plan` and `SeriesQueryBuilder`; `ColumnMetadata` accepting `categories` `single` or `multiple`; `IndicatorQueryRequest` ending with `Overall`; `IndicatorQueryResponse` ending with `Overall` and then `NoData`; `ExportParts.stat` as `{ value, description, dimmed? }` (the image draws a dimmed figure at reduced opacity); `ReportWidget` ending with the positional `CaptionHidden` and the init property `ReferenceLines`; `DashboardBases(MinN, ShowN)`. A stat tile's n line is drawn today by widget-view under the tile, like any widget's, until this change draws it inside the tile (D3). The production-shapes fixture holds 30 shapes, and the ratio-shape plan goldens of `ProductionShapesTests` are compared after `WithoutFigures()` removes the figure outputs. The initial UI bundle is 674.96 kB against the 675 kB warning budget.

## Goals / Non-Goals

**Goals:**
- One rule for the figure's size on every surface that draws it, with no setting, and no number ever broken.
- Statistics computed in SQL over every matching row, with the box plot's method, so a median tile and a box plot over the same rows and filters read the same median.
- Widgets without the new fields keep byte-identical stored JSON, request bodies, SQL and responses: the production-shapes fixture proves it.
- One rule for a ratio over several answers of a declared `single` column, the rule `add-small-sample-warnings` uses for the n (the largest per-answer sum, decided with the user on 2026-11-04), so a value, its denominator and its n never disagree.

**Non-Goals:**
- Fixing an undeclared ratio over several answers. The form hints; the engine changes nothing.
- A per-tile font size, colors for tiles, comparisons with another indicator.
- Statistics on grouped kinds, or a statistic of the per-row values of a pre-aggregated table being made meaningful (see Risks).
- Measures summed over several answers: a count of mentions is a legitimate figure, and the program limits the guard to ratios.
- Save-time warnings and MCP warnings (`add-authoring-guards`).

## Decisions

### D1. The figure's size: container units, one rule

- `StatWidget`'s root becomes a size container (`[container-type:size]`): every host has a definite height (Context), so size containment cannot collapse it.
- The value: `font-size: clamp(1.125rem, min(13cqi, 30cqh), 1.875rem)` (18 to 30 px), `line-height: 1.15`, weight 600, `overflow-wrap: normal` and `word-break: normal` (no `break-all`), `text-wrap: balance`, horizontal overflow clipped with `overflow-x: clip` (Tailwind `overflow-x-clip`), not `overflow: hidden`, and `title` set to the whole value. The coefficients 13 and 30 are the starting point; task 2.1 tunes them on the real tiles of Teatro (3×3, 4×2, 3×2, 12-wide) and records them here. The spec fixes only the bounds. A headless Chrome check on 2026-11-05, over the compiled `styles.css` and the tile's markup (not the real grid), found that 13 and 30 give the expected sizes, and that `overflow: hidden` clips the descenders at a line height of 1.15 while `overflow-x: clip` keeps them; the check's harness was not kept, so task 2.1 still measures on the real stack.
- The description and the secondary lines stay `text-sm` and `text-xs`. The block stays centered while it fits and starts at the top when it does not (`justify-center-safe`), the rule `add-widget-context` D5 gave a tile with a subtitle or a footnote. It holds for every tile, with or without texts or lines (the real-stack check found that a 2-column tile at 768 px cut the top of a three-line figure under plain `justify-center`), so the figure stays whole and the label and the lines are the part cut. The small-base note of a tile (`add-small-sample-warnings` D11) is drawn inside the tile, first among its lines, and not under it, so it takes its room from the label and the lines and never from the figure.
- **Short tiles.** The body of a default 3×2 tile is 81 px high (`add-widget-context` D5: a 160 px tile less the 53 px header, the 24 px of padding and the 2 px border). Today's 36 px figure (a 40 px line) and its 20 px label take 64 px of it, and a one-line subtitle (16 px) with a one-line footnote (20 px) leave 45 px, so that tile keeps its figure whole and cuts its label. The value shrinks first, through `cqh`: in a body of 45 px `30cqh` is under the floor, so the figure is 18 px (a line of about 21 px) and its label fits again, and the same tile with no texts draws about 24 px. Task 2.1 measures both on the real tiles; if the label does not fit, the floor or the line height is tuned within the spec's bounds and the finding is recorded here. `add-small-sample-warnings` measured the case it left to this change (its finding F5): a 3×2 tile with a subtitle, a footnote and the n line under it has a body of 87 px (not 81), of which the 36 px figure (a 40 px line) gets a 23 px box, so about 57 % of it shows. Once this change draws the n line inside the tile, the line is cut with the label, and an 18 px figure (a line of about 21 px) fits in that box whole (scenario "Tile with texts and the n line"); task 2.1 measures it. The narrow 3×2 tile with a long unit that `add-widget-context` found wrapping its figure onto two lines at 36 px ("52% de los hogares") holds it on one line at these sizes. A tile without secondary lines keeps today's description, so it looks as before apart from the figure. A tile with secondary lines limits its description to two lines (`line-clamp-2`) and each line to one (`truncate`), with the whole text in `title`, and a tile short of room keeps its figure whole and cuts the label and the lines, as `dashboard-indicators` "Widget context in a tile" says of the label. The image, which has no fixed height, writes them whole. The lines' checkboxes in the form say that a tile 3 rows high has room for them. What the texts alone take from a tile does not change: a 3×2 stat tile with a 500-character footnote still loses its figure on paper (the finding of `add-widget-context`), and the form's warning (`textsCrowd`) stays the remedy.
- A word wider than the tile at 18 px (a 1-column tile with a 9-digit number) is clipped at the edge; its text stays whole in the DOM, so screen readers read it, and `title` shows it when pointed at.
- **Image.** `ExportParts.stat` (`{ value, description, dimmed? }`, the description null when the widget hides its caption, `dimmed` from `add-small-sample-warnings`) gains `size` (the value's computed font size in px, read with `getComputedStyle` when the parts are asked for) and `secondary` (the lines as shown). `composeImage` in `image-layout.ts` writes the value at `size`, clamped to 18..30 as a guard, wrapped with a new `wrapWords()` that never cuts a word: when one word is wider than the line, the picture widens to fit it, as a wide table widens it. Then the description at 14 px, when it has one, and each secondary line at 12 px, before the notes below, the footnote and the footer. A tile that hides its caption still shows its lines.
- **Print.** Same DOM: the container units resolve against the box on paper. No `paper:` rule is needed; task 2.4 checks it.
- **Email.** 20 px instead of 24 px (`ReportHtml.Stats`); mail programs have no container units.

*Alternatives:*
- *A smaller fixed class (`text-2xl` or `text-3xl`).* Rejected: a fixed size overflows a 2-column tile and looks lost in a 6-column one.
- *A script that measures and shrinks the text.* Rejected: a layout pass per tile (Teatro has 16), a frame at the wrong size, and printing would have to run it again; container units work in print.
- *A size setting per tile.* Rejected: the user asked for a smaller default, and a setting would have to reach every surface. It can come later on `display`.

### D2. The statistic (`config.statistic`)

- **Stored.** `WidgetConfigInput.Statistic` and `WidgetConfig.Statistic`, `string?`, appended last (after `Display` and the fields earlier changes of the program append, such as `missingFooter`), `[JsonIgnore(Condition = WhenWritingNull)]` with a `Description` naming the four values in lower case and no enum (nullable fields, as `WidgetDisplay`). `Normalize()` maps an empty string to null and keeps a value as given. Constants `StatStatistics` (`median`, `p25`, `p75`, `mean`). It is top level, not in `display`, because it changes the rows (program rule 2).
- **Validation** (`CheckConfig` → new `CheckStatistic`, key `{prefix}statistic`):

  | Rule | Message |
  |---|---|
  | not one of the four | "The statistic must be median, p25, p75 or mean." |
  | chart type known and not `stat` | "Only a stat tile has a statistic." |
  | chart type null (a query without one) | "A statistic needs the chart type stat." |

  The last rule departs from the habit of skipping per-kind rules without a chart type, because the planner needs the kind to know it must not sum.
- **Twins.** `queryFor` adds `...(type === 'stat' && config.statistic ? { statistic: config.statistic } : {})`, left out when unset so the key and the body of every existing widget are unchanged; `WidgetQuery.For` passes `Statistic: chartType == ChartTypes.Stat ? config.Statistic : null` by name after the positional arguments. `savedConfig` keeps it through `queryFor`, so a kind change in the form drops it. Shared cases in `query-for.spec.ts` and `WidgetQueryTests.cs`.
- **SQL.** `Plan`, for `chartType == stat` with a statistic, after `plotted` and `rowFilter`, whatever `groupBy` the request carries:

  ```sql
  SELECT NULL::text, {stat}, NULL::text
  FROM (SELECT ({plotted}) AS x {, the base or denominator column} FROM {from}
        WHERE {rowFilter} AND ({plotted}) > '-Infinity'::double precision
              AND ({plotted}) < 'Infinity'::double precision{filters}) v   -- also drops NULL and NaN
  HAVING count(*) > 0
  ```

  `{stat}` is `percentile_cont(0.5) WITHIN GROUP (ORDER BY x)`, `0.25`, `0.75`, or `sum(x) / count(*)` for the mean (not `avg`, so it fails on the same data a sum fails on, box plot D3). A ratio's `plotted` is the row's own `num / nullif(den, 0)`, so a zero denominator is left out. The statement also returns the tile's n (D10) over the rows `v` keeps: `count(*)`, the number of values, or `sum` of the base column, which `v` then carries, when the indicator declares one. Its answer is one `IndicatorRow`, so the page, the email and MCP read it as they read any tile. It is one statement in the existing transaction, under the slot and the 25 s limit, and it reads every matching row: the row limit is never reached.
- **Format.** The indicator's format and unit, the widget's own unit taking the place of the indicator's (`add-widget-context`: `withWidgetUnit` on screen, `MetaOf` in the email), as any tile: a `count` median of 4.5 reads `5`. The box plot's two decimals for a count are not taken, because the tile shows one headline figure that the study's own cards show as whole pesos ("60,514 pesos", "800,000 pesos"), and `add-locale-formatting` brings `display.decimals` for whoever wants them.
- **Named.** The description becomes "Median of {what}", "First quartile of {what}", "Third quartile of {what}", "Mean of {what}" (`indicators.stat.of.*`; C# `ReportText` `statMedian`, … with `{0}`), where `{what}` is what `plotted()` and its C# twin `ReportDataBuilder.Plotted` give: the indicator's label with the names of the measure or of the ratio's columns, or the widget's own caption text (`add-widget-context`) when it has one. The statistic's name is part of the rest of the line, which an own text leaves in place (`dashboard-indicators` "Widget caption text": "The rest of each line SHALL stay"), so a tile whose caption text is "pesos por boleta" reads "Median of pesos por boleta". `plotted()` itself is not changed. A tile whose widget hides its caption hides the statistic's name with it; the name stays in the tile's accessible name, as the caption does.

*Alternatives:*
- *Route through `BoxQueryBuilder.Build(group: null)`.* Rejected: it computes whiskers and outliers that a tile does not need and returns boxes, which every consumer of a tile would have to read differently.
- *A statistic on `display`.* Rejected: it changes the rows, so it must be in the query twins.
- *Two decimals for a count.* Rejected above.

### D3. Secondary lines (`config.display.secondary`)

- **Stored.** `WidgetDisplay.Secondary`, `IReadOnlyList<string>?`, `WhenWritingNull`, values `n` and `unfiltered` (`StatSecondaryLines`), appended last, after `ShowN` (the last member `add-small-sample-warnings` appended), so the existing members keep their place in the JSON. `Normalize()` maps an empty list to null and keeps the order as given; `WidgetDisplay.Normalize()` returns null only when every display field is unset, `secondary` included (program rule 3). `displayFor` keeps it for `stat` only. The tile draws `n` first whatever the stored order. The form writes `["n", "unfiltered"]` order when the member changes the choice and keeps the stored list otherwise, as the orientation does (box plot D1), so a form saved unchanged stays unchanged.
- **Validation** (`CheckDisplay`, key `{prefix}display.secondary`): an unknown value, "Each secondary line must be 'n' or 'unfiltered'."; a repeated one, "A secondary line is listed twice."; any other kind (skipped when the chart type is null), "Only a stat tile has secondary lines."
- **`n` is drawing only.** `add-small-sample-warnings` returns the widget's `n` for a stat tile's query when its indicator declares a base column or an answer column, and words it ("n = 476 Hogares", the name of the base column, else of the denominator, from `add-indicator-column-metadata`). The statistic's statement returns it for a tile with a statistic, always (D10), worded "n = 37" for a number of values and "n = 4 Hogares" for a base column. The tile shows that text when the response has an `n`; it never queries for it. On a stat tile, that change's base n line is drawn by the tile as this line, under the value and once: it shows when `display.secondary` holds `n` or when the line is in force for the tile (`display.showN`, else the dashboard's `showN`), and widget-view draws no second n line under a stat tile.
- **`unfiltered` is a flag of the query request, not a stored field and not a config field**, as `add-chart-annotations` D4 makes `overall` (decided with the user on 2026-11-04: the derived query flags of the program travel as request flags). `IndicatorQueryRequest` gains `bool? Unfiltered` (`WhenWritingNull`, appended last, after that change's `Overall`, with a `Description` saying that the page and the server derive it and that no widget stores it). `WidgetConfigInput` and `WidgetConfig` do not change for it, so no stored config, no widget tool's schema, no `queryFor` or `savedConfig` output and no widget endpoint's body can hold it. The flag is not validated: where it cannot apply (a chart type other than `stat`, no dashboard filter that narrows the tile) it does nothing and raises no error, and `CheckConfig` knows nothing of it.
  - **Who sets it.** Two twins decide it from the saved config: `WidgetQuery.Unfiltered(chartType, config)` in the API and `unfilteredFor(type, config)` in `widget-view.ts`, true for a stat tile whose `display.secondary` holds `unfiltered` and false otherwise. Their shared cases go in `query-for.spec.ts` and `WidgetQueryTests.cs`, as program rule 2 asks of the query twins. `queryFor` and `WidgetQuery.For` do not change for it: the config they build is the same with the line checked or not.
  - **Who sends it.** The page: `IndicatorsService.query` gains an optional argument after `overall` and sends `unfiltered: true` only when it is true, so every other request body is byte for byte today's. The view's key adds `unfiltered: true` only then, so the key of every other widget is unchanged; checking the line adds it, so the preview queries again, and checking `n` changes nothing in the key. The widget form's preview is the same view and follows. The email, the widget workbook and `get_widget_data`: `QueryAsync` gains an optional `unfiltered` argument next to `overall`, and `ReportDataBuilder.ReadWidgetAsync` and `McpDashboardTools.WidgetDataAsync` pass `WidgetQuery.Unfiltered(widget.ChartType, widget.Config)`. The widget workbook is built from the saved config its request carries (`savedConfig`, display included, which `add-widget-context` made the page send) by the same `ReadWidgetAsync`, so one call covers the email and the workbook. The query endpoint passes `request.Unfiltered == true` (`IndicatorEndpoints.QueryAsync`). MCP's `query_indicator` sends no dashboard filters, so nothing narrows its tile and there is no figure to compare with: it sets no flag and takes no `unfiltered` argument, and no tool's input schema has an `unfiltered` property.
  - **With the reference lines.** A stat tile has no reference line, and `add-chart-annotations` plans its overall statement on the plain grouped path only, never for a stat tile, so a request never carries both flags.
- **SQL.** `QueryAsync` passes its `unfiltered` argument to `Plan`, as it passes `overall`. `Plan` returns `Unfiltered: IndicatorSql?` when the flag is set, the kind is `stat`, and the dashboard filters it was given narrow the rows (`PlanDashboardFilters` produced a WHERE: a filter the table lacks or the widget ignores does not count). It is the same plan with the widget's own filters and no dashboard filters (the statistic's statement when the tile has one, D4's corrected form when it applies). `QueryAsync` runs it after the first statement, in the same transaction, and returns its `rows[0].value` as `IndicatorQueryResponse.Unfiltered` (`double?`, `WhenWritingNull`, appended last, after `NoData`, which `add-small-sample-warnings` appended after `Overall`). With no row it is left out.
- **Words.** "Without filters: {value}" / "Sin filtros: {value}", formatted as the tile. "Without filters" follows the program; the widget's own filters still apply, which the docs say.

*Alternatives:*
- *A top-level `unfiltered` field stored in the config.* Rejected: the program puts the choice on `display.secondary` with `n`, and one stored list keeps the form and MCP simple. The flag is derived by both twins instead.
- *`unfiltered` inside `WidgetConfigInput`, set by `queryFor` and `WidgetQuery.For` (this design's first form).* Rejected with the user on 2026-11-04, for `add-chart-annotations`' reasons: `WidgetConfigInput` is the schema of `create_widget`, `update_widget` and `query_indicator` and of the widget endpoints in OpenAPI, so the flag would show there as a setting that saving silently drops; `savedConfig`, which spreads `queryFor`, would have to strip it again; and the preview's key would carry it in every widget's `config`. A second pattern next to `overall` for the same kind of flag was the cost of that form.
- *Always run the second statement.* Rejected: it would add a statement to every tile while any filter is set (67 tiles in production).

### D4. A ratio over declared answers

The rule applies only when the widget plots a ratio, where `aggregate` sums it: plain grouped kinds, stat tiles without a statistic, the `ORDER BY` of a sort by value, every branch of the series statement, and `add-chart-annotations`' overall statement (a stat tile's statement, so the line and a tile with the same filters still agree). Measures, statistics, box plots and the per-row histogram are not touched, and neither are the series and pie domain statements, which only rank and must not refold or recolor anything.

`QueryAsync` already reads the indicator's answer columns for the n (`add-small-sample-warnings` D5, `IndicatorBases.Answers`). This change adds each column's kind to it, and `Plan` takes the answer columns declared `single` (S) and `multiple` (M). When the declared columns mix the two kinds, all of them are taken as `multiple`, the safe side, so S, when not empty, is every declared column. With no declaration, or a measure, the SQL is byte-identical to today's.

**D4a. `single`: the base counted once across answers.** **Decided with the user on 2026-11-04:** the rule is the n's own (`add-small-sample-warnings` D3, the largest per-answer sum), used now, not the program's first rule (once per cell). Each value or total that spans several answers divides the sum of its numerators by the largest of its per-answer denominator sums, taken over its own rows: per group when the widget groups by another column (each comuna of a chart by `comuna`), per series value and per cell. An answer is one combination of the declared columns, grouped together by the helper `BaseQueryBuilder` uses for the n. A mark at level L (no column for a tile, the grand total and the overall value; the group, the series, or both) takes:

```sql
SELECT {L}, sum(num)::double precision / nullif(max(den), 0)
FROM (SELECT {L}, {S}, sum({num}) AS num, sum({den}) AS den, count(*) AS n {, the sums or minimums the statement also needs}
      FROM {from} WHERE {rowFilter}{filters}
      GROUP BY {L}, {S}) a
GROUP BY {L}
```

- When each mark's rows hold one answer (bars grouped by `categoria` over one question, a filter that keeps one answer, or a group column that moves with the answer, such as `orden`), each mark has one inner group, and the result is the ratio of sums, as before.
- When a mark spans several answers (a tile with `categoria` in four values, a comuna's column with `categoria` in four values, the "Total" over the answers, an "Other" series that folds answers), `max(den)` takes the base once: in a single-choice question every unit is in the denominator of every answer, so each answer's sum is the same n.
- **Which columns to declare** is `add-small-sample-warnings`' advice (its D3): the question, code and answer columns of a long table (`variable`, `orden`, `categoria`). For a widget over one question the answer column alone is enough: a code column that moves with it (`orden` "01" for "1. Sí") changes nothing, because the sums are taken per answer, and declaring it too is harmless, since the declared columns are grouped together. The question column matters for a widget that spans several questions whose answers share names.
- Duplicate rows of one answer are still summed (the inner group), so "Duplicate rows summed" holds. Row counts stay table rows (`sum(n)`); a map's numeric tooltip columns are carried as sums and its text ones as minimums; a numeric sort column and the geometry are carried as their minimums.
- In the series statement, `src` keeps its series text and kind, and `grp`, `cell`, the series totals and the grand total each take the nested form at their level, grouped also by S. The rank of `grp` takes the corrected value, so a sort by value follows what is drawn.
- The figures `add-small-sample-warnings` returns for a mark are this `sum(num)` and `max(den)`, so a tooltip's denominator matches the value; its n (`BaseQueryBuilder.Counted`) is the same largest per-answer sum when no base column is declared.

**D4b. `multiple`: refused when a plotted value spans several answers.** Decided with the user on 2026-11-04: the refusal stays (the alternatives were figures with a note, and leaving it to `add-authoring-guards`).
- Before the main statement, whenever M is not empty, `Plan` adds a check over the same rows, per plotted value. A widget grouped or split by the answer column passes it, since each of its values holds one answer; one grouped by the question column (`variable`) with every answer kept does not:

  ```sql
  SELECT count(DISTINCT {m1}), count(DISTINCT {m2}) … FROM {from} WHERE {rowFilter}{filters}
  GROUP BY {group}{, series} HAVING count(DISTINCT ({M})) > 1 LIMIT 1
  ```

  (no `GROUP BY` for a tile). When it returns a row the response has `combinedCategories` (`string?`, `WhenWritingNull`, appended last: the column of M with the most distinct values in that row, the last in the table's column order on a tie, so `categoria` in the study's long tables, which publish `variable`, `orden`, `categoria` in that order), no rows, `published: true` and no missing columns; neither the main nor the unfiltered statement runs.
- The columns of M are taken together as the answers of one question.
- The check is on the data, not on the config, so a tile whose question has one answer in its rows ("Sin dato de precio (E7)") is not refused, and a dashboard filter that keeps one answer lets the widget draw.
- **Totals and folds.** Whenever M is not empty, the values that can span answers although every plotted value holds one take `CASE WHEN count(DISTINCT ({M})) > 1 THEN NULL ELSE {aggregate} END`: the value of `grp`, the series totals, the grand total, the overall statement and the unfiltered statement. A cell has no null value (`IndicatorRow.Value` is a number), so a folded "Other" cell that spans answers is left out by putting the same condition in its `HAVING`. The `HAVING` and the rank of `grp` keep today's `aggregate`, so no group is dropped and the order is unchanged. "Show as table", the emails and MCP already show a null total as "—" or nothing (`dashboard-reports` "Missing values in widget tables"); a reference line with no value is not drawn (`add-chart-annotations` D3).
- **The message** (page `indicators.combined.*`, email `ReportText.combinedCategories`, MCP English): "`categoria` holds the answers of a multiple-choice question. Adding up several of them counts a respondent once for each answer. Keep one answer, group or split the widget by `categoria`, or plot a row the indicator publishes for any of them."
- It is a query-time answer, not a save-time 400. A widget saved before its indicator was declared must show the message, not fail; the form's preview shows it before saving; MCP's `query_indicator` returns it.

*Alternatives:*
- *Group by every other column, take each cell's denominator once, sum (the program's first idea, once per cell).* Rejected with the user on 2026-11-04, as `add-small-sample-warnings` D3 rejected it for the n: every long-format table publishes `orden` next to `categoria`, so each answer would be its own cell unless the author declared every column that moves with the answer, and a value and its n would be counted by two rules.
- *Skip the `multiple` check when the group or the series is declared.* Rejected: with the question column declared as `add-small-sample-warnings` advises, a bar chart grouped by `variable` with every answer kept would add up answers unchecked. The check is one `EXISTS` over the same rows, run only for indicators with a `multiple` column.
- *Refuse in `CheckConfig` from the config alone* (an `in` with several values, or no filter, on a declared column). Rejected: it would refuse tiles whose question has one answer in the rows, such as Teatro's "Sin dato de precio (E7)", the day `teatro_hoy` is declared.
- *Divide each row's denominator by the number of answers in its cell with a window function.* Rejected: one per-row factor cannot serve marks at different levels at once (bars by answer and the "Total" over the answers).
- *`sum(den) / count(DISTINCT answer)` per mark.* Rejected: wrong as soon as a cell lacks a row for an answer, or a mark spans several questions.
- *Refuse a whole series widget when a total spans answers.* Rejected: its cells are right; only the totals are not.

### D10. The n of a tile with a statistic

**Decided with the user on 2026-11-04:** a stat tile with a statistic (median, p25, p75, mean) has as its n the number of values the statistic covers, as a box plot's box has its number of values (`add-small-sample-warnings` D2), when its indicator declares no base column: the median tile of "Pagó por la última boleta (E7)" reads "n = 37". When the indicator declares a base column, the n is the sum of that column over the same rows ("n = 4 Hogares").

- **Counted over the values.** The rows the statistic covers are the rows `v` keeps (D2): after the widget and dashboard filters, with a finite value. A row whose ratio has a zero denominator, or no value, is in neither the statistic nor its n.
- **No declaration needed.** The values are rows, each one unit, so the n is right without answer columns; a declared answer column changes nothing here, since a statistic never sums rows. This is the exception to `add-small-sample-warnings`' rule that a widget's n needs a declaration (its D4), as a box is.
- **Where it goes.** It is the response's `n` and the row's `n` of the tile, so it is the tile's n line (D3), its small base (dimmed below the threshold in force), the email's and the workbook's lines (D7) and MCP's `n` (D8), with no new field. The line reads "n = {count}" with no name for a number of values, and "n = {sum} {name of the base column}" for a base column.
- **No numerator or denominator sums.** `add-small-sample-warnings` returns, for each value of a ratio, the sums of its numerator and denominator. A tile with a statistic divides each row by its own denominator, so those sums would describe a ratio the tile does not show; its statement returns the value and the n only, and the response, the email and MCP carry no `numerator` or `denominator` for it (decided with the user on 2026-11-05; `dashboard-indicators` "Widget query over one indicator").
- **A tile without a statistic** keeps `add-small-sample-warnings`' rule: the sum of the base column, else of the denominator, and a widget n only with a declaration.

*Alternatives:*
- *No n for a statistic over a measure with no base column* (the rule this design first kept). Rejected with the user on 2026-11-04: authors typed "n = 37" into titles, and the count is known and right.
- *The sum of the denominator for a ratio statistic.* Rejected: each row is one value of the statistic, so the number of values is what it covers.

### D11. Released with `add-small-sample-warnings`

**Decided with the user on 2026-11-04:** this change ships in the same release as `add-small-sample-warnings` (its D17). That change is implemented and archived first, then this one, and neither is deployed alone.

- An indicator can declare answer columns only from that release on, and this correction applies from the same release, so no declaration ever exists while ratios over several answers are added up as separate bases, and no ratio changes value under an author's feet after a later deploy.
- No list of declared indicators is needed before the deploy (Migration Plan).
- Both are rolled back together.

*Alternative:* release this change after `add-small-sample-warnings` and list the indicators declared in between. Rejected: it leaves a window where a tile's value and its n disagree.

## Risks / Trade-offs

- **[The smaller figure is visible on every tile at once]** → It is the requested default. Task 2.1 checks Teatro's 16 tiles at 1,280 and 390 px before release, and the bounds are in the spec.
- **[A very narrow tile clips a long number]** → The floor is 18 px, so only tiles of about one column clip; the whole value is in the DOM and the `title`, and the image widens instead of cutting.
- **[A statistic over a pre-aggregated table means nothing]** (the median of category shares) → The form's hint, the MCP help and the docs say a statistic needs a table with one row per unit. Nothing detects it.
- **[No answer has a row in every cell]** (a pre-aggregated table that drops empty answers) → the largest per-answer sum then undercounts the base, for the value as for the n. Every long-format table of the study keeps every answer in every cell (block() puts every household in every answer's denominator); the docs say a declared table must, and an integration test pins the behavior when one answer is missing from some cells.
- **[A question's answers are declared `single` but are multiple-choice]** → The correction then gives "mentions per household". The docs say to declare `multiple` when in doubt; mixed columns are declared `multiple`.
- **[The hint fires on columns that move with the group]** (Escuelas f139) → It is only text in the form and never blocks saving.
- **[One more statement for "Without filters"]** → Only for tiles that ask, only while a filter narrows them, in the same slot and transaction under the 25 s limit.
- **[A declared indicator's totals change]** → That is the correction, after the author opts in; documented with the example. No declaration exists before it, since both changes ship together (D11).
- **[A value over the answers of several single-choice questions]** (a bar "Sí" over two questions, with `variable` and `categoria` declared `single`) → its numerators are not disjoint, so the corrected value can pass 100 %, while its n is right. Such a value divided by k × n before, which was wrong too. The docs and `Mcp/Instructions.md` say to filter or split by the question column.
- **[n of a statistic over a table that is not one row per unit]** → the number of values counts rows, not units, as a box's does. The same hint that says a statistic needs a table with one row per unit covers it.
- **[The twins drift]** (`queryFor`/`WidgetQuery.For` for the statistic, `unfilteredFor`/`WidgetQuery.Unfiltered` for the flag, `plotted`/`Plotted`) → Shared cases in `query-for.spec.ts` and `WidgetQueryTests.cs`, and the fixture.
- **[A 3×2 tile with texts and lines is short of room]** (a one-line subtitle and footnote leave 45 px, and a line or two more do not fit) → The figure stays whole and the label and the lines are the part cut (`justify-center-safe`, D1), as `add-widget-context` made the label the part cut; the form's note says a tile 3 rows high has room. Task 2.1 measures that the label itself fits again with two one-line texts and no lines, and records it.
- **[The UI bundle goes over its warning budget]** (674.96 kB against 675 kB after `add-small-sample-warnings`; this change adds the tile's lines, the form's fields and hint, and strings) → Measure the build after group 6 rather than only at the end, reuse existing Tailwind utilities, and avoid that change's two pitfalls: the bare word `transform` in a source or spec file adds a utility (+0.49 kB), and `image-layout.ts` must import `small-base-style.ts`, never `base-figures.ts`. Task 8.2 records the size; if it passes the warning budget, the user decides whether to raise it before release.
- **[The value and its n counted by two rules]** → One rule, settled with the user on 2026-11-04: this change reuses `add-small-sample-warnings`' largest per-answer sum and its answer grouping (`BaseQueryBuilder`), and an integration test checks that each mark's `denominator` and the widget's n equal the corrected denominator (task 3.4).

## Migration Plan

1. **Release.** This change ships in the same release as `add-small-sample-warnings` (D11, decided with the user on 2026-11-04), never alone. No indicator can declare answer columns before that release, so nothing has to be listed before the deploy.
2. **Deploy.** No DbUp script of its own: no column and no stored config change (`add-small-sample-warnings`' migration, numbered 0023 after the archived 0021 and 0022, runs in the same release). Deploy the `api` and the `ui` together. Until a tile opts in or an indicator declares answers, the only difference is the smaller figure.
3. **Rollback** (program section 2, rule 7). This change and `add-small-sample-warnings` are rolled back together, to the release before both:
   - An older `api` ignores `statistic` and `display.secondary` when it reads a config, and drops them the next time that widget is saved. A tile with a statistic would show the sum of its rows meanwhile, which is a wrong figure. Before rolling back, list them: `SELECT d.name, w.title FROM tamiza.dashboard_widgets w JOIN tamiza.dashboards d ON d.id = w.dashboard_id WHERE w.chart_type = 'stat' AND (w.config ? 'statistic' OR w.config -> 'display' ? 'secondary');`, and tell their authors or remove them.
   - An older `api` ignores the request's `unfiltered` flag (an unknown property of the body is dropped), so it never returns the figure and a newer `ui` against it draws no "Without filters" line; an older `ui` never sends the flag and ignores `unfiltered` and `combinedCategories` in responses. No widget stores the flag, so nothing needs cleaning up.
   - The `categories` declarations belong to `add-small-sample-warnings`, whose Migration Plan says what the older `api` does with them: it ignores them, so declared indicators go back to today's sums, including the wrong ones, with no n. Since the two are rolled back together, no release applies the declarations to the n without this correction.
   - The figure goes back to 36 px.
   - Dashboard versions keep the fields in their content, and restoring one on a newer release brings them back.
