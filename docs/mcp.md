# Working with Tamiza from Claude (MCP)

Tamiza has an MCP server (Model Context Protocol) so an AI client such as Claude can work with a project the way an analyst does: read the Kobo form and summaries of the data, propose indicators, write and test the scripts, run the chain and build the dashboard and its widgets. You ask in a conversation ("describe the access to water by municipality with the last survey") and Claude does the steps with the tools below, as you, with your role.

- **Tamiza calls no model.** The AI client brings the model; your own Claude plan pays for it. The MCP server makes no outbound request.
- **It is off until the operator turns it on, and each project is off until its admin allows it.** Two locks decide how much of a project's data a client can see (see [Allow a project](#allow-a-project-project-admin)).
- **Claude acts as you.** Every call runs with your account and your role in the project, exactly as the interface does, and every change is attributed to you.

## Turn it on (operator)

1. Register the client in Keycloak: [Client for AI clients (MCP)](keycloak.md#client-for-ai-clients-mcp-optional). Without it nobody can sign in.
2. In `.env`, set `TAMIZA_MCP_ENABLED=true` and, only if projects may allow rows, `TAMIZA_MCP_MAX_DATA_ACCESS=rows`. The other variables have defaults; see [`.env.example`](../.env.example) and [docs/operations.md](operations.md#mcp-server-optional).
3. `docker compose up -d api ui` (the `ui` image carries the proxy locations for `/mcp` and `/.well-known/oauth-protected-resource`).
4. Check `https://<your address>/.well-known/oauth-protected-resource/mcp`: it must answer a short JSON document that names `https://<your address>/mcp` and your Keycloak realm.

**Who can connect.** claude.ai, Claude Desktop and the mobile apps connect from Anthropic's servers (the range `160.79.104.0/21`), so `TAMIZA_PUBLIC_URL` and Keycloak must be reachable from the Internet over HTTPS. Claude Code connects from the analyst's own computer, so it works on a private network when that computer reaches Tamiza and Keycloak. If your installation is private and people use claude.ai, Anthropic documents MCP tunnels for that case.

## Allow a project (project admin)

In **Settings > General** the card **AI clients (MCP)** shows the project's level. Every project starts at *Off*, new and existing. The admin chooses:

| Level | What a client can see |
|---|---|
| **Off** | Nothing. Every tool that names the project answers that an admin can allow it. |
| **Summaries only** | The form, the tables and columns with their types and question labels, row counts, *column profiles*, the scripts, the shape of test and run results with masked errors, and what indicators and widgets show. Never rows. |
| **Summaries and rows** | Also rows of the raw, clean, output, indicator and reference tables, previews of tests, the values a script passes to `ctx.show`, and unmasked errors and logs. |

The operator's maximum (`TAMIZA_MCP_MAX_DATA_ACCESS`, summaries by default) limits every project: a project set to *Summaries and rows* under a *summaries* maximum behaves as *Summaries only*, and the card says so. Changing a level takes effect on the next call.

Below the level the card lists the project's 50 most recent calls (when, who, which tool, the outcome), so the team can see what Claude did.

## Connect (every person)

Open **Connect an AI client** in Tamiza's top bar. It shows the address, the client ID and these steps with your values filled in.

**claude.ai and Claude Desktop.** *Customize > Connectors > Add custom connector*, paste the address (`https://<your address>/mcp`), open the advanced settings, choose **Use your own OAuth client** and enter the client ID (`tamiza-mcp` unless the operator changed it). Leave the secret empty: the client is public. Press Connect and sign in with your Tamiza (Keycloak) account.

**Claude Code.**

```text
claude mcp add --transport http --client-id tamiza-mcp --callback-port 33418 tamiza https://<your address>/mcp
```

then run `/mcp` inside Claude Code and sign in. Claude Code keeps working while your Keycloak session lasts, and for as long as the connection's refresh token lives when the realm allows offline access.

**Revoke.** Remove the connector in Claude, and revoke the application in your Keycloak account page (*Applications*, the link is on the connect page). An operator can end every connection by removing the Keycloak client or by turning `TAMIZA_MCP_ENABLED` off.

## What the client sees

- The **column profile** (`profile_table`) describes a column over all its rows without returning any: how many are empty or distinct; for numbers the minimum, quartiles, mean and maximum (a minimum of -99 shows a sentinel to clean); for dates the earliest and latest; for yes/no columns the counts; for select questions the count of each choice label (a count under 5 is reported as "fewer than 5"); and for short text columns the values that 5 or more rows share. Free text is never listed.
- **Test and run results** show the shape of every table and, for an indicator, how its table will look on a dashboard. Errors and log lines are masked as the script assistant masks them: only the exception, the lines of the script and the words that come from the schema, the libraries or your own script survive; any other word or number shows as `…`. Printed output and previews are not included unless rows are allowed.
- **What reaches the client at every level, including summaries:** the choice labels of the form (a list of enumerators' names is part of them), the question labels, the code of your scripts, the names and settings of dashboards, the values that indicator queries and widgets show (what a viewer sees on a dashboard), the field metrics of the performance dashboard (including the names of enumerators), the minimum and maximum of numeric columns, and values that 5 or more rows share in short text lists. Do not type secrets or personal data into scripts as constants.
- Choosing a level and a Claude plan is a data-protection decision of your organization (in Colombia, Ley 1581 and the rules of the donors of a study). What Anthropic does with conversations depends on the plan's terms, which your organization checks; this page is not legal advice.

## The tools

Every tool runs the same code as the interface's own action, with the same checks and limits. The role is the one the interface needs for the same action.

| Group | Tool | Role | What it does |
|---|---|---|---|
| Orientation | `list_projects` | any member | Your projects, your role in each and the access AI clients have there |
| | `get_project` | viewer | State of a project: submissions, published tables, indicators, dashboards; for analysts also the last synchronization, scripts and last run |
| The Kobo data | `get_form` | analyst | Questions, choice lists (`list` reads one in full), form versions in use, enumerator question, metrics the form supports |
| | `get_tables` | viewer (`clean`, `output`, `indicators`), analyst (`raw`, `reference`) | Tables of a source with columns, types, question labels, the select question each column answers, row counts |
| | `profile_table` | as `get_tables` | Column profiles of one table, 40 columns per call |
| | `get_fieldwork` | viewer | The performance dashboard's metrics for a range of days |
| | `query_rows` | as `get_tables`, and rows allowed | Up to 100 rows of a table with the clean data dashboard's filters and one sort column |
| Scripts | `get_authoring_guide` | analyst of a project AI clients may use | The script contract, `ctx`, libraries, conventions and templates |
| | `list_scripts`, `get_script`, `list_script_versions` | analyst | Scripts with their current version numbers, any version's code, the history |
| | `save_script`, `remove_script`, `restore_script_version` | analyst | Write a script as a new version; earlier versions stay and can be restored. An indicator also takes the names of its table's columns (`columns`, see **Column labels** below) |
| Tests and runs | `test_script`, `get_test` | analyst | Try a draft on a sample without publishing anything, waiting up to two minutes |
| | `start_run`, `get_run` | analyst | Queue a run and read it |
| Indicators | `list_indicators`, `get_indicator_columns` | viewer | Indicators with their publish state and the labels of their columns, and the columns of a table, each with its `label` when its indicator gives one |
| | `query_indicator` | viewer | What a widget would plot, without saving anything; with a series column it returns the series, the cells and the totals |
| Dashboards | `list_dashboards`, `get_dashboard`, `get_widget_data` | viewer | Dashboards, their filters, palette, colors kept by value, source and widgets, and what the widgets show |
| | `create_dashboard`, `update_dashboard`, `duplicate_dashboard`, `remove_dashboard` | analyst | Add, rename, move, set the filters, the colors (`palette`, `valueColors`) and the source of, copy and remove dashboards |
| | `create_widget`, `update_widget`, `remove_widget` | analyst | Add, change, move to another dashboard and remove widgets of any kind, including the series settings (`seriesBy`, `layout`, `pyramid`, `scale`) and a widget's color, scale, column labels, texts, reference lines, steps, data labels or the order of its values (`display`) |
| | `list_dashboard_versions`, `get_dashboard_version` | analyst | A dashboard's kept versions with what changed, author, time and origin, and any kept version's name, filters, palette, colors kept by value, source and widgets |
| | `restore_dashboard_version` | analyst | Restore a kept version of a dashboard as a new version |

**Widgets with two dimensions.** The widget tools take every chart type of the dashboard: `stat`, `bar`, `column`, `line`, `histogram`, `pie`, `map`, `heatmap`, `pyramid`, `likert`, `crosstab` and `boxplot`, and the settings that go with a second column (see [indicators-dashboard.md](indicators-dashboard.md#widgets-with-a-series)). A refused setting answers `mcp.validation` with its key (`config.seriesBy`, `config.layout`, `config.pyramid.right`, `config.scale[1].side`), and nothing is saved. For a widget with a series, `query_indicator` and `get_widget_data` return `series`, `cells`, `totals` and `notes` instead of `rows`; a result that is too long is cut from its `cells`. A `boxplot` returns `boxes` instead of `rows`: for each box its `group`, `values`, `min`, `q1`, `median`, `q3`, `max`, `mean`, `lowerWhisker`, `upperWhisker` and `outlierCount`, and the same figures as the indicator formats them in `formatted` (a `count` indicator's figures have two decimals). The values of the outliers are not returned, and a result that is too long is cut from its `boxes`. A `boxplot` takes no `seriesBy`; `sort` = `{ by: "value", direction }` orders its boxes by median, and `config.display.orientation` (`vertical`, the default, or `horizontal`) draws it.

**Column labels.** An indicator's script names its columns for code (`numerator`, `denominator`, `comuna`), and every widget shows those names unless someone gives a column a name for people (see [Column names](indicators-dashboard.md#column-names)).

- `save_script` takes for an indicator an optional `columns`: `{ column: { label } }`, each label of 1 to 80 characters with no line break, for at most 100 columns, keyed by the column's name in lower case (`{ "numerator": { "label": "Hogares que asistieron" }, "denominator": { "label": "Hogares" } }`). **Left out, the current version's labels are kept**, unlike the label, the description and the unit, which each save replaces; `{}` clears them, and given, it replaces them all. A column is named as its table publishes it and is not checked against the published table, so a label can be saved before the first run. A refused label answers `mcp.validation` with its key (`columns.numerator.label` for a label too long or with a line break, `columns` for a key that is not a column's name or for more than 100 columns), and no version is created. For script 1 and script 2 `columns` is ignored. Restoring a version of the script brings its labels back.
- `get_script`, `list_indicators` and the answer of `save_script` return `columns` when an indicator has labels, and `get_indicator_columns` gives each column its `label`.
- A column that widgets group or split by can also take, in the same `columns`, an `order` (its values as full text, in the order to draw them, up to 100, none twice), `last` (up to 20 values kept at the end whatever the order or the sort, such as `Otro`, `No sabe` or `Sin dato`, none also in `order`) and `stripPrefix: true` (hides a leading number such as `1. ` in what widgets show; filters and colors kept by value still use the full text), each value up to 500 characters. A column may have only these, without a label. The map is replaced whole, so a client re-sends each column's settings with its name; `get_script`, `list_indicators` and `get_indicator_columns` return them. A broken rule answers `mcp.validation` with its key (`columns.categoria.order`, `columns.categoria.last[0]`) and no version is created. A property that is not one of these is ignored. See [Order of values](indicators-dashboard.md#order-of-values).
- A widget's own order is `display.order` in the `config` of `create_widget`, `update_widget` and `query_indicator`: `{ group, series }`, each a list of up to 100 values as full text; the values it does not list follow in the chart's order. `group` is refused with a sort (a box plot's order by median included) and where the widget has no group column, `series` where it has no series column and on a pyramid or a Likert widget, with `mcp.validation` on `config.display.order.group` or `config.display.order.series`. `query_indicator` and `get_widget_data` list `rows`, `series`, `cells` and `boxes` in the order the widget declares, each value with its full text (a client writes filters from them); a widget that declares nothing gets them as before.
- A widget's own names are `display.labels` in the `config` of `create_widget`, `update_widget` and `query_indicator`: `{ column: name }` for up to 10 columns, each of 1 to 80 characters, on every kind of widget. A column takes the widget's label, else its indicator's, else its own name. Too many labels, a label that is too long and a key that is not a column's name are refused with `mcp.validation` on `config.display.labels`.
- `get_widget_data` and `query_indicator` return `labels` for each widget: the name shown for each column it names (its measure or its ratio's two columns, its group and series columns, and the tooltip columns of a map that have no label of their own) that has a label, its own or its indicator's. A widget whose columns have none has no `labels`.
- A widget's texts are `display.subtitle` (1 to 200 characters), `display.footnote` (1 to 500), `display.caption` (`{ text }` of 1 to 200 characters, which replaces the indicator's name wherever the widget names what it plots, or `{ hidden: true }`, which leaves the caption line out of sight while tooltips and tables still name what is plotted), `display.unit` (1 to 32 characters, which replaces the indicator's unit for that widget) and `display.showDescription: true` (a button that shows the indicator's description), in the `config` of `create_widget` and `update_widget`, on every kind of widget (see [Words around a widget](indicators-dashboard.md#words-around-a-widget)). None of them may hold a line break or another control character, and a caption cannot have both its own text and `hidden`. A refused value answers `mcp.validation` on `config.display.subtitle`, `config.display.footnote`, `config.display.caption`, `config.display.caption.text` or `config.display.unit`, and nothing is saved. A new `config` replaces the old one whole, so `update_widget` sends `display` again, texts included, when it changes the query: a `config` without them removes them, as it removes a color. `query_indicator` only previews a query and keeps the indicator's unit.
- `get_widget_data` formats each widget's values with its own `unit` when it has one, and returns its `subtitle`, `footnote` and own `caption` text beside its `labels`; a widget that has none of them returns none of these.
- A widget's chart annotations are `display.referenceLines`, `display.interpolation` and `display.dataLabels`, in the `config` of `create_widget` and `update_widget` (see [Reference lines, steps and data labels](indicators-dashboard.md#reference-lines-steps-and-data-labels)). `display.referenceLines` is up to 4 lines on a bar, column or line, `[{ kind, value, label }]`: `kind` is `mean` or `median` (of the bars or points drawn; not with a `seriesBy`), `overall` (the ratio's value over all the widget's rows, as a stat tile with the same filters shows it; it needs a ratio, and over the answers of one question it is only the mean of the bars, not a total) or `value` (a number in the indicator's units, 0.5 for 50%; the only kind with a `value`, and in a `percent` layout a share from 0 to 1). `label` is optional, 1 to 40 characters with no line break; left out, the line reads `Mean`, `Median`, `Overall` or `Reference`. `display.interpolation` is `linear` (the default) or `step`, for a line only. `display.dataLabels: true` writes each value on a bar, column (with no `seriesBy`, or `grouped`), line or pie. A refused value answers `mcp.validation` on `config.display.referenceLines`, `config.display.referenceLines[i].kind`, `config.display.referenceLines[i].value`, `config.display.referenceLines[i].label`, `config.display.interpolation`, `config.display.dataLabels` or `config.display.order`, and nothing is saved: a fifth line, a line on a chart that is not a bar, column or line, a `mean` or `median` with a `seriesBy`, an `overall` over a measure, a `value` line with no number, a share outside 0 to 1 in a `percent` layout, a label with a line break, steps on a chart that is not a line and data labels on a stacked or `percent` layout. A new `config` replaces the old one whole, so `update_widget` sends `referenceLines`, `interpolation` and `dataLabels` again when it changes the query.
- `get_widget_data` and `query_indicator` (when it is given a `chartType`) return `referenceLines` for a widget that has lines: `[{ kind, label, value, formatted }]` for each line drawn, with the English default label when the line has none and `formatted` written like the widget's other values (with the widget's own unit in `get_widget_data`, the indicator's in `query_indicator`; a share for a layout stacked to 100%). A line with no value, such as an `overall` over rows whose denominators sum to 0, is left out, and a widget without lines returns no `referenceLines`. `query_indicator` previews an `overall` line with the same statement a stat tile with the same filters runs and saves nothing.

**Colors.** A dashboard is drawn in one palette and can keep a color for chosen values, as the **Colors** action of the page does (see [Colors](indicators-dashboard.md#colors)).

- `palette` is `tamiza` (the default), `institutional`, `earth` or `vivid`. `valueColors` is `[{ column, value, color }]` with `color` from 1 to 8, a place in the palette and never a color code: `{ "column": "sex", "value": "Female", "color": 5 }` gives `Female` color 5 in every widget of the dashboard that colors by `sex` (see [Colors kept by value](indicators-dashboard.md#colors-kept-by-value)).
- **Names are matched exactly.** `palette` and the scales of `display.ramp` are written in lower case as listed here, and nothing is trimmed or corrected: `Vivid` or `Green` is refused with `mcp.validation` on `palette` or `config.display.ramp`. An empty `display.ramp` is read as not set, but an empty `palette` is refused. In `valueColors`, `column` is a column's name as an indicator table publishes it, in lower-case letters, digits and underscores (`Sex` is refused, on `valueColors[0].column`). Only its shape is checked, so a well-formed name that no indicator table publishes is saved and colors nothing: a misspelled column is not caught, and `get_indicator_columns` gives the real names. `value` is matched as exact text, case and spaces included: `female` does not give `Female` its color, and the two can each keep a color. A NUL character in a value is refused on `valueColors[i].value` ("The value cannot contain a NUL character."). A `color` must be a whole number: a fraction such as 3.5 is refused as a malformed argument, on `arguments` and not on the color key. A key that is not listed is ignored, not refused, so check the spelling: `display: { "colour": 3 }` sets no color, and a column given `{ "label": "Hogares", "colour": "red" }` is saved with its label only.
- `update_dashboard` sets them with the other settings it takes (`name`, `position`, `filters`, `source`), and any one of the six is enough. `valueColors` is the whole list, replacing the current one, and an empty list removes them all. A call that gives only `palette` keeps the colors kept by value, and one that gives only `valueColors` keeps the palette. Read `get_dashboard` first to add to the list. The call answers with the dashboard's `palette` and `valueColors` as saved.
- `get_dashboard` and `get_dashboard_version` return `palette` and `valueColors`; a version recorded before palettes reads `tamiza` with no colors kept. `duplicate_dashboard` copies both.
- A widget's own color or scale is the `display` of its `config` in `create_widget` and `update_widget`: `display.color` (1 to 8, color 1 when left out) for a bar, column or line chart with no `seriesBy`, for a histogram and for a box plot, and `display.ramp` (`blue`, `teal`, `green`, `orange`, `red`, `purple` or `gray`, the palette's own scale when left out) for a map or a heat map (see [Widget color and scale](indicators-dashboard.md#widget-color-and-scale)). A widget with a series takes its colors from its series, and another kind has no color of its own. A widget's `display.labels` is the third thing it holds (see **Column labels** below). A new `config` replaces the old one whole, so `update_widget` sends `display` again, labels included, when it changes the query: a `config` without `display.labels` removes the widget's own labels. Only `update_widget` changes the `chartType` of a widget. Changing the `chartType` of a widget that has a color, a scale, an orientation, reference lines, steps, data labels or an order also needs a `config` without the `display` fields the new type does not take: a new `chartType` alone keeps the old `config`, so it is refused, with an error on `config.display.color`, `config.display.ramp`, `config.display.orientation`, `config.display.referenceLines`, `config.display.interpolation`, `config.display.dataLabels` or `config.display.order`, when the new type does not take them.
- A refused value answers `mcp.validation` with its key (`palette`, `valueColors`, `valueColors[1].color`, `valueColors[2]` for a value or a color a column already uses, `config.display.color`, `config.display.ramp`, `config.display.orientation`, `config.display.referenceLines`), the same as the page's, and that part is not saved. A call that gives none of `name`, `position`, `filters`, `palette`, `valueColors` and `source` is refused.
- Saving a palette or colors that change something is a version of the dashboard, whose `changes` list `colorsChanged` (the page words it "Colors changed"; the kinds of change are listed under **Versions of dashboards**). A call that renames the dashboard and sets its colors makes one version, as any request does (below), and a call that sets what the dashboard already has makes none.
- A dashboard's source says where its data comes from, such as the survey (see [Dashboard source](indicators-dashboard.md#dashboard-source)). `update_dashboard` sets it with `source`, 1 to 300 characters with no line break; left out, the source stays as it is, and an empty text removes it. A source that is too long or holds a line break is refused with `mcp.validation` on `source`, and nothing is saved. The call answers with the `source` as saved, and `get_dashboard` and `get_dashboard_version` return it when the dashboard or the version has one. Saving a source that changes it is a version whose `changes` list `sourceChanged` (the page words it "Source changed"), and a call that renames the dashboard and sets its source makes one version.

**Versions of dashboards.** Every change to a dashboard's name, filters, colors or widgets is recorded as a version, and each dashboard keeps its last 10 (see [indicators-dashboard.md](indicators-dashboard.md#version-history)). The source is part of what a version holds, and changing it makes a version too. The dashboard writes (`create_dashboard`, `update_dashboard`, `duplicate_dashboard`, `create_widget`, `update_widget`, `remove_widget`) and `restore_dashboard_version` take `change`: a few words, 1 to 120 characters, saying what you asked for, such as "Add five water indicators". Claude passes the same `change` on every write it makes for one request, so the writes of a request make one version of each dashboard they change, shown in the version history as yours, marked "via MCP", with that text. A write by the same person with the same `change` (ignoring case and surrounding spaces) joins the dashboard's newest version when it comes less than 30 minutes after the previous one and nothing else changed the dashboard in between; otherwise it makes a new version, and a restore is always a version of its own. A call without `change`, or with a blank one or one longer than 120 characters, is refused with `mcp.validation` on `change`, and saves nothing; `remove_dashboard` takes none, since a dashboard's versions go with it. Moving a dashboard to another place among the project's is not a change to it: `update_dashboard` with only a `position` makes no version.

- Each write's result has `dashboardVersions`: the current version of every dashboard it changed, `[{ dashboardId, version }]`, both dashboards for a widget moved between them. `get_dashboard` gives the dashboard's `version`, and each entry of `list_dashboards` its own.
- A call that saves part of what it was asked and is then refused, such as `update_dashboard` renaming a dashboard and refusing its filters or its colors, still records what it saved.
- `list_dashboard_versions` gives the kept versions, newest first, with what changed (`changes`, the first 20, and `moreChanges` for the rest; the kinds are listed below), who, when, `origin` (`app` or `mcp`) and `note` (the `change`). `get_dashboard_version` gives a version's name, filters, palette, colors kept by value and source (when it had one) as `get_dashboard` gives them, and its widgets with their `id`, title, chart type, `config` and layout (no `dashboardId` or `updatedAt`), to compare before restoring or to add one widget again with `create_widget`.
- `restore_dashboard_version` brings back the version's name, filters, palette, colors kept by value, source and widgets as a new version, so the state it replaces stays in the history and the restore can be undone too. It answers `restored`, the new `version`, `restoredFrom`, the `name`, `nameKept` (true when another dashboard now has the version's name, so the current one is kept) and `copies` (each widget of the version that another dashboard now holds, restored as a copy with a new id). When the dashboard already is as in that version it answers `restored` false and changes nothing.
- To undo a request, Claude restores, on every dashboard the request's results named, the version before the request's. When the request moved a widget, it restores first the dashboard the widget went to, so the widget comes back to the other one with its identifier.
- A version older than the 10 kept, or one that was never recorded, is refused by `get_dashboard_version` and `restore_dashboard_version` with `dashboards.versionNotFound` (see [Troubleshooting](#troubleshooting)).

**The kinds of change.** Each entry of `changes`, in `list_dashboard_versions` and `get_dashboard_version`, is `{ kind, widget?, dashboard?, version? }`, and the `kind` is what a client reads: the page words each kind as a sentence, `colorsChanged` as "Colors changed". The fields after `kind` are left out when the kind does not use them.

| `kind` | What it records | Also gives |
|---|---|---|
| `initial` | The dashboard as it was when version history began, kept as its version 1 | |
| `created` | The dashboard was added, alone or with its project | |
| `duplicated` | The dashboard is a copy | `dashboard`: the original's name |
| `renamed` | The dashboard was renamed | `dashboard`: the new name |
| `filtersChanged` | The filters were saved | |
| `colorsChanged` | The palette or the colors kept by value changed | |
| `sourceChanged` | The dashboard's source was set, changed or removed | |
| `widgetAdded` | A widget was added | `widget`: its title |
| `widgetChanged` | A widget's title, chart type, query or display (color, scale or column labels) changed, with or without its position and size; its texts are part of its display | `widget`: its title after the change |
| `widgetRemoved` | A widget was removed | `widget`: its title |
| `widgetMovedOut` | A widget went to another dashboard | `widget`, and `dashboard`: where it went |
| `widgetMovedIn` | A widget came from another dashboard | `widget`, and `dashboard`: where it came from |
| `layoutChanged` | Widgets were moved or resized and nothing else of them changed | |
| `restored` | A restore brought back an earlier version | `version`: the number brought back |
| `unrecorded` | A state no version held, which a restore recorded before replacing it | |

There is also the prompt `describe_situation` (a project and a situation), which starts the work described below.

## A worked session

> **You:** Use Tamiza to describe the access to drinking water by municipality in my "Water survey" project.

1. Claude calls `list_projects` and `get_project`, then `get_form` and `get_tables` to see the questions (`water_source`, `municipality`) and the tables, and `profile_table` on `main`: "`water_source` has Piped 812, Well 390 and River under 5; `household_size` has -99 in 6 rows".
2. It proposes: "I would build `piped_water_rate` (households whose main source is piped, over all households, by municipality) and count `households`. I will treat -99 as missing. Do you confirm?" You answer.
3. With `get_authoring_guide` it writes script 1 (turn -99 into empty) and `test_script`s it; it reads the shape of the result and the masked error if any, fixes the draft and tests again. Then `save_script`.
4. The same for each indicator, saving `piped_water_rate` with its label, `%` unit and `percent` format.
5. `start_run` and wait; `get_run` shows the steps.
6. `create_dashboard` "Water access", `query_indicator` to check each widget, `create_widget` for a stat tile, a bar by municipality and a map, `update_dashboard` for a Municipality filter, all with the `change` "Build the water access dashboard", and `get_widget_data` to read it back. It tells you what the dashboard shows and what to look at.

The calls appear in Settings > General. Everything Claude saved is a new version of a script (Versions tab, marked "via MCP"), so you can restore any earlier one. The dashboard's request is one version of it (Version history, marked "via MCP" with the request): ask Claude to undo it, or restore the version before it yourself.

## Guards

- **Saves need the version you read.** `save_script`, `remove_script` and `restore_script_version` take `baseVersion`, the version number from `list_scripts` or `get_script` (omitted for a script that does not exist yet). If someone saved in the meantime the call is refused with `mcp.scriptChanged` and the current version's author and time; nothing changes. `restore_dashboard_version` takes `baseVersion` too, the dashboard's current version from `list_dashboard_versions` or `get_dashboard`: if a version was recorded in the meantime, by a member in Tamiza or by another request, the call is refused with `mcp.dashboardChanged` and the current version's number, author, time and origin; nothing is restored.
- **Removals name what they remove.** `remove_dashboard` needs the dashboard's name and `remove_widget` the widget's title, compared ignoring case. A wrong identifier cannot remove the wrong thing: `mcp.nameMismatch`. A removed widget stays in the dashboard's kept versions, so it can be added again or brought back by a restore; a removed dashboard takes its versions with it and cannot be brought back.
- **Code that reaches outside the script is refused.** `save_script`, `restore_script_version` and `test_script` refuse code that imports `os`, `sys`, `subprocess`, `socket`, `shutil`, `ctypes`, `importlib`, `http` or `urllib`, calls `__import__`, `eval`, `exec`, `compile` or `open`, or holds a web address (`mcp.unsafeCode`, with the lines). The script editor still accepts such code from a person, with warnings. This is a line scan, not isolation: scripts run without a strong sandbox, and the text of a form or of the data could mislead a client, so allow rows only for projects whose scripts you can review.
- **Limits.** A person runs at most 4 calls at once and 120 a minute across all their clients (`mcp.rateLimited`, with the seconds to wait). A result longer than 60,000 characters is cut from the end of its longest list and says which list and which argument asks for less. A test started from Claude replaces your own queued test in the project, as a new test in the editor does.
- **Records.** Each call is recorded with who, which project, which tool, the level, the outcome and the size of the result, never its arguments or its result, and kept 180 days. A call refused for a limit is recorded once a minute for a person, so a client that keeps calling past its limit cannot fill the table.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Claude says it cannot reach the server | The address is not public HTTPS (claude.ai needs it), or `/.well-known/oauth-protected-resource/mcp` does not answer, or Keycloak is not reachable from the Internet |
| Sign-in loops or fails at Keycloak | The client's redirect URIs lack `https://claude.ai/api/mcp/auth_callback` or `http://localhost:<port>/callback`, or the audience mapper is missing: [the Keycloak section](keycloak.md#client-for-ai-clients-mcp-optional) has a check |
| Tools that name the project say `mcp.projectOff` | An admin of the project has not allowed AI clients in Settings > General. `get_authoring_guide` names no project and says `mcp.forbidden` until the person is an analyst or admin of one the admin allowed |
| A tool says `mcp.validation` about `arguments`, or `mcp.notFound` about a tool | The client sent a malformed argument, such as a value of the wrong type or a fraction where a whole number goes (a `color` of 3.5), or the name of a tool that does not exist: it should read the tool list again. A required argument left out is reported under its own name instead |
| A dashboard write says `mcp.validation` about `change` | The client did not give `change`, or gave a blank one or one longer than 120 characters: every dashboard write needs the request in 1 to 120 characters. It should read the tool list again |
| `restore_dashboard_version` says `mcp.dashboardChanged` | The dashboard changed after Claude read its versions: it should read them again and decide what to restore |
| `query_rows` says `mcp.rowsNotAllowed` | The project is at *Summaries only*, or the operator's maximum is `aggregates` |
| A call says `mcp.timeout` | A table is being replaced by a run, or a profile took too long: name fewer columns, or try again |
| `create_dashboard` or `duplicate_dashboard` says `dashboards.limit` | The project already has 10 dashboards, the most it can have (`status` 409). Remove one with `remove_dashboard`, after asking the person which, and call again |
| A tool that names a dashboard says `dashboards.notFound` | The project has no dashboard with that `dashboardId`: another member removed it, or it is another project's or mistyped (`status` 404). `list_dashboards` gives the ones it has. `get_dashboard`, `get_widget_data`, `list_dashboard_versions`, `get_dashboard_version`, `restore_dashboard_version`, `duplicate_dashboard`, `remove_dashboard`, `create_widget`, `update_widget`, `remove_widget` and `update_dashboard` with a name, filters, palette or colors all answer it |
| `get_dashboard_version` or `restore_dashboard_version` says `dashboards.versionNotFound` | The dashboard keeps only its 10 newest versions, and the number asked for is older than those or was never recorded (`status` 404). `list_dashboard_versions` gives the numbers kept |

A refusal that comes from a rule the page applies too, and has a code of its own, such as the last three rows of this table, keeps the page's code instead of an `mcp.` one and adds the HTTP `status`: `{ "code": "dashboards.limit", "message": "...", "status": 409 }`.
